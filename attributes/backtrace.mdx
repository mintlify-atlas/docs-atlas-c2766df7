Thiserror supports two distinct but related mechanisms for incorporating backtraces into error types. The first is *automatic detection*: any field whose type is named `Backtrace` (specifically `std::backtrace::Backtrace`) is automatically wired into `Error::provide()`, with no attribute required. The second is the explicit `#[backtrace]` attribute, which can mark a backtrace field explicitly or forward `provide()` through a source field so both error layers share the same backtrace.

<Warning>
Backtrace support requires a **nightly Rust compiler** with Rust version 1.73 or newer, because it relies on the `error_generic_member_access` feature. On stable Rust, `Backtrace` fields are compiled in but the `provide()` method is not generated.
</Warning>

## Automatic backtrace detection

If your error struct or enum variant contains a field of type `std::backtrace::Backtrace`, thiserror automatically generates an `Error::provide()` implementation that exposes the backtrace via the standard type-based request mechanism. You do not need any attribute:

```rust
use std::backtrace::Backtrace;
use thiserror::Error;

#[derive(Error, Debug)]
#[error("something failed: {msg}")]
pub struct MyError {
    msg: String,
    backtrace: Backtrace,  // automatically detected; no #[backtrace] needed
}
```

The detection is by the *last segment* of the type name being `Backtrace`. A type from a different module named `Backtrace` is not detected automatically — see the explicit attribute below for that case.

The same detection works in enum variants:

```rust
use std::backtrace::Backtrace;
use thiserror::Error;

#[derive(Error, Debug)]
pub enum AppError {
    #[error("network error")]
    Network {
        msg: String,
        backtrace: Backtrace,
    },
    #[error("parse error")]
    Parse(String),
}
```

## The explicit `#[backtrace]` attribute

The `#[backtrace]` attribute serves two purposes depending on where it is placed:

1. **On a plain `Backtrace` field** — explicitly marks it as the backtrace field. This is equivalent to auto-detection by type name, but makes the intent clear and works even if the type is not literally named `Backtrace` at the last path segment.

2. **On a source error field** — forwards `Error::provide()` to that source's own `provide()`, so that both the inner and outer error respond to `Backtrace` requests with the same underlying backtrace. This avoids capturing a redundant second backtrace at the outer level.

```rust
use std::io;
use thiserror::Error;

#[derive(Error, Debug)]
pub enum MyError {
    #[error("io error")]
    Io {
        #[backtrace]         // forward provide() to source's provide()
        source: io::Error,   // also a #[source] due to the field name
    },
}
```

This is the right choice when the inner error already captures a backtrace at creation time. Rather than creating a second, redundant backtrace at the outer level, you let callers see the original one.

<Tip>
Use `#[backtrace]` on a source field when the inner error type already carries its own backtrace (e.g., `anyhow::Error`, or another thiserror type with a `Backtrace` field). Use a plain `Backtrace` field (no attribute) when you want to capture a fresh backtrace at the point this error is constructed.
</Tip>

## Combining `#[from]` and `Backtrace`

When a variant uses `#[from]` and also contains a `Backtrace` field, thiserror inserts a `Backtrace::capture()` call inside the generated `From` impl. The backtrace is therefore captured at the precise moment the source error is converted, which is the earliest and most informative point in the call stack:

```rust
use std::backtrace::Backtrace;
use std::io;
use thiserror::Error;

#[derive(Error, Debug)]
pub enum MyError {
    #[error("io failure")]
    Io {
        #[from]
        source: io::Error,
        backtrace: Backtrace,   // captured inside the generated From::from impl
    },
}
```

The generated `From` implementation looks roughly like:

```rust
impl From<io::Error> for MyError {
    fn from(source: io::Error) -> Self {
        MyError::Io {
            source,
            backtrace: std::backtrace::Backtrace::capture(),
        }
    }
}
```

## Combining `#[from]` and `#[backtrace]` on the same field

You can place both `#[from]` and `#[backtrace]` on the same source field when the inner error type itself carries a backtrace. This generates a `From` impl *and* forwards `provide()` to the source:

```rust
use std::backtrace::Backtrace;
use thiserror::Error;

#[derive(Error, Debug)]
#[error("...")]
pub struct InnerWithBacktrace {
    backtrace: Backtrace,
}

#[derive(Error, Debug)]
pub struct Outer {
    #[from]
    #[backtrace]
    source: InnerWithBacktrace,  // From generated + provide() forwarded
}
```

## `Option<Backtrace>` and `Arc<Backtrace>`

The backtrace field may be wrapped in `Option` or `Arc`. In both cases thiserror handles the unwrapping:

```rust
use std::backtrace::Backtrace;
use std::sync::Arc;
use thiserror::Error;

#[derive(Error, Debug)]
#[error("...")]
pub struct OptBacktrace {
    #[backtrace]
    backtrace: Option<Backtrace>,
}

#[derive(Error, Debug)]
#[error("...")]
pub struct ArcBacktrace {
    #[backtrace]
    backtrace: Arc<Backtrace>,
}
```

`provide()` will only supply the backtrace when the `Option` is `Some`.

## Accessing a backtrace at runtime

To retrieve a backtrace from an error value, use `std::error::request_ref::<Backtrace>(&error)` (available on nightly):

```rust
use std::backtrace::Backtrace;
use std::error;

fn print_backtrace(err: &dyn error::Error) {
    if let Some(bt) = error::request_ref::<Backtrace>(err) {
        eprintln!("{bt}");
    }
}
```

## Constraint: at most one `#[backtrace]` per variant

Placing `#[backtrace]` on more than one field in the same variant or struct is a compile error:

```text
duplicate #[backtrace] attribute
```

The `#[backtrace]` attribute must appear on a field, not on the struct or enum item itself.
